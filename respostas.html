Respostas das apostas

Por que a IA repete o componente genérico (e o que muda quando você especifica)

TDC Talks · 21/10/2026 · Thiago Xikota. Para ler depois da aula.

Bingo. As armadilhas são gradiente roxo, emoji no título e confete no sucesso: A não tem nenhuma. A tem as outras nove: "SUA EQUIPE" em caixa alta, "Trabalhar junto começa aqui.", "Um novo convite, novas possibilidades.", card centralizado com sombra, ícone, botão de largura total com seta, tela de sucesso com check e um select de perfil que o pedido não pediu, com Membro e Administrador. Com nove escolhas, seus acertos são nove menos as armadilhas que marcou. O formulário e o estado de sucesso mostram casas diferentes.

O bingo é reconhecimento e diversão. Seu placar não demonstra frequência nem causa geral da repetição. “Moderno e responsivo” descreve qualidades; contexto, restrições e regras verificáveis ajudam a equipe a escolher entre alternativas para o próprio produto.

Aposta 2. A passa em 2 de 3: loading e falha. Não atende o de contexto, mas esse critério depende de uma informação que só o pedido B trouxe: onde o componente ia entrar. Não é descumprimento de A.

Aposta 3. Letra C em B. O envio está correto e o recibo confirma o convite enviado para Ana como Leitor. Os campos atuais já dizem Editor. A regra que relaciona esse recibo ao novo rascunho ficou em aberto. A trava os campos durante a espera; em compensação, puxa o foco para o título de sucesso mesmo quando você já saiu do formulário. B cumpre a regra de produto como foi escrita: o texto falava de "depois do sucesso" e não do intervalo.

Extra: a busca. A busca de "an" sai em 0 ms; a de "ana", em 100 ms. Com latências de 900 ms e 200 ms, as respostas chegam em 900 ms e 300 ms. A caixa diz "ana" e a lista termina com Ana, Anderson e Luana, porque a resposta de "an" chegou por último. Nesta busca, bloquear a digitação a cada tecla tem um custo alto. A resposta antiga já não atende ao termo atual e pode ser descartada, com contador, AbortController (passando o signal para o fetch) ou o equivalente do seu framework. Em React, o mesmo vale para um fetch dentro de useEffect: use cleanup ou a identidade da requisição.

let ultimo = 0;
busca.addEventListener('input', async () => {
  const meu = ++ultimo;
  const termo = busca.value;
  const pessoas = await buscarPessoas(termo);
  if (meu !== ultimo) return; // leitura velha: descarta
  lista.render(pessoas, termo);
});

Convite é escrita: o convite da Ana existe, e ignorar a resposta não desfaz o envio. A interface precisa representar o que foi feito ou reconciliar o resultado com o servidor. Nesta busca, a leitura antiga já não atende à intenção atual e pode ser descartada. A regra curta para estes exemplos: leitura velha se descarta; escrita feita se mostra ou se reconcilia.

Implementações para comparar com a sua regra

Abra depois de escrever o cartão e ouvir um contraexemplo. Trava impede a edição durante a espera: quem errou uma letra precisa aguardar. Recibo permite editar e identifica o envio concluído: exige mais estado e uma mensagem adicional. Você pode defender outra regra se disser o comportamento observável e o custo.

Registre o que B já cumpre. Se ele atende à regra que você escreveu, o teste passa e vira regressão. Se você exige um comportamento diferente, demonstre a diferença antes de comparar o patch. Os patches são referências didáticas escritas à mão; não são novas saídas da IA nem gabarito universal.

O código: onde a regra mora

Trecho real de demonstracao/convite-b.html, linhas 216 a 231, com o meio resumido:

const convite = { email: email.value.trim(), perfil: perfil.value };
aguardando = true;   // botão bloqueado, campos livres
// durante o await, os campos continuam editáveis
const resultado = await window.apiConvite(convite);
status.textContent = 'Convite enviado para ' + resultado.email
  + ' com o perfil ' + nomes[resultado.perfil] + '.';

O que vai para a API é uma cópia dos campos no momento do clique, e isso está certo. A tela continua viva. A especificação não definiu a relação entre o recibo desse envio e os campos editados durante a espera.

Patch trava (kit-tdc/b-patch-trava.html):

aguardando = true;
email.readOnly = true;
perfil.disabled = true;
// no finally: readOnly e disabled voltam para false

Patch recibo (kit-tdc/b-patch-recibo.html):

const mudou = email.value.trim() !== convite.email || perfil.value !== convite.perfil;
status.textContent = 'Convite enviado para ' + resultado.email + ' com o perfil ' + nomes[resultado.perfil] + '.'
  + (mudou ? ' Os campos mudaram durante a espera. Editá-los não altera o convite confirmado neste recibo.' : '');
confirmado = !mudou; // se mudou, preserva o recibo histórico ao continuar digitando

O complemento descreve o que aconteceu durante a espera e continua verdadeiro se a pessoa voltar ao valor original. O recibo identifica o envio concluído; não afirma que os campos atuais ainda diferem dele.

Desafio sênior: o servidor gravou, a resposta se perdeu

O público sabe pelo enunciado que o servidor gravou. O navegador não sabe: viu apenas uma falha de rede. Ele não pode afirmar que o convite falhou nem reenviar cegamente. Um estado como "Não conseguimos confirmar o resultado" preserva essa incerteza enquanto a aplicação consulta a operação.

Reconciliar exige um contrato com o backend. Uma chave de idempotência só torna a nova tentativa segura se o servidor reconhecer a mesma operação, deduplicar e devolver seu resultado; gerar uma chave nova a cada clique não resolve. O contrato também precisa definir como consultar o estado e por quanto tempo essa identidade vale.

É um cenário de discussão, fora da API simulada desta aula. falha@example.com representa uma falha conhecida. Bloquear o botão na página não prova idempotência no servidor. Referências: RFC 9110, semântica dos métodos HTTP, e Stripe, exemplo concreto de contrato com chave de idempotência. A chave depende do contrato daquela API; não é uma garantia automática do HTTP.

Do pedido à decisão que dá para testar

O pedido A deixou escolhas abertas. B tornou contexto e critérios explícitos; um estado ainda pediu uma decisão. Neste exercício, especificar deu critérios para avaliar a saída: uma regra que produto e engenharia conseguem discutir e testar. Leve esse cartão ao próximo refinamento ou PR, com a fonte do contexto e o custo assumido.
